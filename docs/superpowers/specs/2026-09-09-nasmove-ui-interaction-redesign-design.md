# NasMove UI 与交互重设计

> 文档日期：2026-09-09
> 状态：待用户审阅
> 范围：PySide6／Qt Widgets 表现层；不改变 SMB、持久化、传输、校验和删除安全协议。

## 1．目标与已确认决策

此次改造将 NasMove 从四页串行向导重构为以“迁移工作台”为中心的单窗口体验。用户已确认以下视觉与交互方向：

1. 采用“迁移指挥台＋运行概览”的复合结构：创建任务与已运行任务属于同一工作台，而非两个割裂页面。
2. 保留三套可切换主题：雾蓝玻璃、深夜运维、暖灰工作室；用户可随时切换。
3. 创建态、执行态与恢复态采用同一导航、同一信息层级和同一安全语义。
4. 执行页将复制与完整回读校验明确分开，不能把复制 100％呈现为迁移成功。
5. 网络中断／NAS 重启时优先说明“数据正被怎样保护”，展示自动恢复步骤，并只给出安全的人工操作。

设计目标：减少页面跳转和重复信息，提升创建任务、理解传输状态与恢复中断任务时的可预测性，同时不得弱化源文件安全、校验或恢复边界。

非目标：不迁移至 SwiftUI，不改动 SMB 协议实现，不修改 SQLite schema，不改变任务状态机，不引入新的第三方运行时依赖。

## 2．现状与问题

当前 `MainWindow` 使用 `QStackedWidget` 在连接、来源、目标和任务队列四页之间切换。页面标题、步骤文字、上一页／下一页按钮由窗口统一控制；任务队列又拥有自己的左右分栏详情区。

这种结构的业务安全性没有问题，但交互上存在三个缺口：

1. 创建迁移与观察现有任务互相排斥。用户进入新建流程时无法同时看见活跃任务、等待恢复任务或队列。
2. 连接、来源与目标是一个计划的三个条件，却只能跨三页确认，用户无法一眼判断计划是否已具备安全执行条件。
3. 正常执行、等待网络和已完成的视觉结构差异较大；恢复信息和错误详情容易在页面边缘，未先回答用户最关心的“源文件是否安全”。

现有的 `ConnectionPage`、`SourcePage`、`TargetPage`、`TaskPage` 及其控制器已经承载了连接测试、来源选择、目标浏览、任务创建、执行事件和安全说明。改造必须复用这些行为和信号，而不是把传输逻辑搬入 View。

## 3．信息架构与导航

窗口采用持久左侧导航、顶部全局栏和中间单一工作区。

| 导航项 | 职责 | 中心区状态 |
|---|---|---|
| 迁移工作台 | 创建计划、查看当前选中任务的执行或恢复状态 | `setup`、`running`、`recovery`、`empty` 四选一 |
| 任务队列 | 浏览、选择和调整待执行任务 | 队列列表与任务摘要；选择后可返回工作台 |
| 连接配置 | 管理 NAS 配置与测试连接 | 连接配置列表或编辑器 |
| 历史与报告 | 查看已完成、失败和导出的脱敏摘要 | 历史结果列表与详情 |
| 偏好设置 | 主题与外观偏好 | 主题选择与“跟随系统”开关 |

顶部栏显示 NasMove 品牌、主题快捷入口；当存在活动或等待恢复的任务时，显示紧凑状态胶囊，例如“1 个任务正在处理”。点击胶囊进入任务队列；不在创建区复制整套监控面板。

窄窗口下左侧导航折叠为图标栏；中心区纵向堆叠准备卡片。不得以缩小输入控件高度或截断文字换取布局空间。

## 4．工作台状态与交互

### 4.1 创建态：`setup`

中心区依次呈现三个准备卡片和一个紧凑的迁移计划面板：

1. **连接**：显示配置名、主机／共享、加密状态与“已验证”结果。点击卡片进入或展开已有连接编辑与测试界面。
2. **来源**：显示选中数量、总大小及目录层级策略。点击后使用既有文件／目录选择与拖放能力。
3. **目标**：显示共享内路径、可用空间与能力预检结果。点击后使用既有远端目录浏览能力。

三项都满足前，主要按钮禁用并说明缺少的条件；满足后显示“加入队列”。入队前保持现有的计划、路径、空间及能力校验。计划面板必须显示复制／安全移动、冲突策略和校验策略：

- 复制：显示“复制 → 完整回读 SHA-256 校验 → 原子提交”。
- 安全移动：在同一链路后追加“确认安全条件 → 删除源文件”；完整校验不可关闭。

创建计划不直接执行 SMB 或扫描逻辑。View 仅调用现有 `TaskCreationController`，由既有服务完成预检、规划、持久化和入队。

### 4.2 执行态：`running`

选择活动任务后，中心区替换为该任务详情：

1. 顶部显示任务名、目标位置、文件数量与总容量。
2. 阶段轨道顺序固定为“复制、完整回读校验、原子提交、源文件处理”。已完成、当前和未开始状态必须可区分。
3. “复制”和“完整校验”使用两条独立进度条，分别显示确认字节、速度和预计剩余时间；总进度仅作辅助信息。
4. 正常状态只展示“暂停”“取消”“查看文件详情”。错误处理记录默认折叠，发生异常时才在主内容区展开。
5. 点击顶部活动任务胶囊或左侧“任务队列”可以切换任务；后台事件不得覆盖用户正在查看的其他任务详情。

现有 `TaskController` 按任务 ID 路由事件、迟到进度不得覆盖终态的行为必须保持。

### 4.3 恢复态：`recovery`

任务处于 `waiting_for_network` 或需要恢复核验时，中心区优先显示黄色注意卡，而不是技术详情：

1. 先说明已保存检查点、未提交半成品、尚未删除源文件。
2. 用三步状态说明“传输已停止 → 等待重连 → 断点核验”。展示下一次自动重试倒计时与重试次数。
3. 提供“暂停并稍后继续”“检查连接”“立即重试”三个操作。取消任务仍使用现有明确的断点／临时文件处置流程，不能在此页新增绕过恢复协议的快捷操作。
4. 只有连续失败、凭据缺失、权限不足或目标状态不确定时，才展开可操作错误原因、脱敏代码与处理记录。

## 5．主题与视觉语言

主题在“偏好设置”中以单选项展示，并提供顶部快捷入口。选择立即生效并持久化；默认使用“跟随系统”，若系统外观无法确定则回退到雾蓝玻璃。

| 主题 | 目的 | 主要调色 |
|---|---|---|
| 雾蓝玻璃 | 默认浅色、清晰而克制的工作场景 | 雾蓝／低饱和蓝紫；白色半透明表面 |
| 深夜运维 | 长时间队列监控与夜间环境 | 深蓝灰表面；蓝青高亮 |
| 暖灰工作室 | 摄影、视频等内容归档场景 | 暖灰纸张底色；琥珀主操作色 |

本项目是 Qt Widgets 桌面应用，不使用 iOS／SwiftUI 专有的 `glassEffect` API。所谓“玻璃”只描述视觉层次：使用低透明度表面、柔和边界、有限阴影和原生 Qt 控件；不得通过高成本实时模糊、复杂动画或自绘特效影响文件传输时的界面响应。

无论主题如何变化，下列语义色与文字必须稳定、对比度足够：已验证／完成为绿色，正在执行为蓝色，等待恢复／注意为黄色，失败／不可安全继续为红色。主题不能只靠颜色表达状态，必须包含图标和文本。

## 6．组件边界与数据流

新增或调整的界面层必须遵循以下职责：

```text
MainWindow
├── AppNavigation（导航与全局活动状态）
├── ThemeController（读取、应用和持久化外观偏好）
└── MigrationWorkbench
    ├── SetupWorkspace（连接、来源、目标和计划摘要）
    ├── RunningWorkspace（活动任务阶段与进度）
    └── RecoveryWorkspace（等待重连和安全恢复）
```

- `MainWindow` 只负责导航、工作区选择和依赖装配，不再内嵌各状态的布局细节。
- `MigrationWorkbench` 根据用户所选任务及其 `TaskState` 切换四个互斥状态；不要使用多个独立布尔值控制同一中心区。
- `SetupWorkspace` 组合现有连接、来源和目标页面的输入／摘要能力，通过 `TaskCreationController` 创建任务。
- `RunningWorkspace` 与 `RecoveryWorkspace` 只订阅 `TaskController` 已安全路由的展示模型；它们不得调用文件、SMB、SQLite 或删除服务。
- `ThemeController` 仅管理配色令牌和用户偏好，不接触任务、凭据、连接参数或日志。

建议影响范围：`src/nasmove/ui/main_window.py`、`task_page.py`、`connection_page.py`、`source_page.py`、`target_page.py`、`task_controller.py`、`task_creation_controller.py` 及其相应 UI 测试。实现时应先核对现有公开属性和信号，避免一次性重写所有页面。

## 7．异常、可访问性与性能

1. 所有错误文案继续使用脱敏错误代码映射；不得在状态卡、主题偏好或导出摘要中泄露密码、SMB 会话或完整敏感路径。
2. 连接测试、目标浏览、计划扫描、传输、哈希和 SQLite 长操作继续在工作线程；主题切换和界面状态转换不得触发这些任务重跑。
3. 每个交互控件须有文本标签、键盘焦点顺序与明确禁用原因；状态不可只通过颜色传达。
4. 保持现有小窗口保护：输入项最小高度、中心内容滚动、详情区域限高且可展开。
5. 进度事件可能高频到达；渲染应只更新当前选中任务的可见字段，并保留现有节流／终态保护语义。

## 8．验收与测试

实现完成后至少验证：

1. 创建态的连接、来源、目标三项缺失／完成状态及“加入队列”启用条件。
2. 复制、校验、提交、源处理阶段分别显示；复制 100％时不可显示为迁移完成。
3. 背景任务事件不会替换当前选择任务的详情；完成结果不会被迟到进度覆盖。
4. 断网、NAS 重启、重试和暂停状态下，恢复卡准确说明检查点与源文件安全边界。
5. 三个主题可切换、重启后保持选择、所有状态文字在浅色和深色主题下可读。
6. 800×620、1100×760、1600×1000 下没有裁切输入框、隐藏主要操作或无法访问的详情。
7. 现有真实 NAS 桌面集成测试继续覆盖连接、规划、入队、执行、校验和完成；主题与 UI 重构不能改变其安全结果。

## 9．实施顺序与回滚

建议分四步实施：

1. 抽取主题令牌与导航壳，保留现有页面行为。
2. 新建工作台状态容器，将现有创建页面嵌入／组合进 `setup` 状态。
3. 将现有任务详情拆为 `running` 与 `recovery` 视图，保持控制器和命令服务不变。
4. 补齐主题、布局、状态路由和真实流程回归测试，再移除不再使用的旧向导布局。

每一步都可通过保持旧 `QStackedWidget` 页面作为内部回退来降低风险。若发生回归，先恢复上一阶段的工作台壳和原页面入口；不得回滚或修改任务库、Keychain 项或 NAS 临时文件来处理 UI 问题。
